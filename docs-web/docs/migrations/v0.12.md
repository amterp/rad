# Migrating to Rad v0.12

Version 0.12 has two breaking changes, and they share a shape: both take a default
that quietly did the wrong thing to text you passed through it, and make the safe
reading the default instead.

- `split()` and `replace()` now match literally, with `regex=true` to opt back in.
- Values interpolated into a shell command are now quoted, so they arrive as one
  argument instead of as shell syntax.

Neither raises an error on the old spelling in every case, so both are worth
reading rather than waiting to be told.

## Breaking Change: `split()` and `replace()` Match Literally

### What Changed

Both functions used to treat their pattern as a regex. Now they look for the exact
text you give them:

```rad
print(split("1.2.3", "."))          // v0.11: ["", "", "", "", ""]   v0.12: ["1", "2", "3"]
print(replace("a.b", ".", "-"))     // v0.11: "---"                  v0.12: "a-b"
```

Pass `regex=true` to get the old behavior:

```rad
print(split("a b  c", "\s+", regex=true))          // -> ["a", "b", "c"]
print(replace("order 66", "\d+", "N", regex=true)) // -> "order N"
```

`matches()` is unchanged. It exists to test patterns, so it's still always a regex.

### Why

Two reasons, and the second is the one that matters.

The first is that literal is what most calls want. Across a corpus of real Rad
scripts, 87% of `split` and `replace` calls passed a pattern with no regex
constructs in it. The default was serving the minority.

The second is how the two mistakes fail. Reaching for a literal when you needed a
regex gives you an obviously wrong answer that you notice immediately. Reaching for
a regex when you needed a literal corrupts quietly: a `.` matches every character,
a `$` in text you relayed from somewhere else eats your replacement. Silent
corruption is the worse failure, and it belonged to the old default.

### Two More Things Changed

**`replace()`'s replacement text is now literal too.** In the default mode, `$1`
and `$$` in the replacement are inserted as written. Previously they were always
interpreted, which meant relaying text through `replace()` could mangle it. Group
references still work under `regex=true`.

**`split()` no longer guesses.** It used to compile the separator as a regex and,
if that failed, silently fall back to a literal split. Whether a call was a regex
split or a literal one was decided at runtime by the shape of the input:

```rad
// v0.11
split("a.b", ".")    // -> ["", "", "", ""]  (a valid regex, so: regex)
split("a(b", "(")    // -> ["a", "b"]        (not a valid regex, so: literal)
```

Now the separator is literal unless you say otherwise, and under `regex=true` a
pattern that doesn't compile is an error.

### Migration Steps

**1. Find the affected calls.** Rad ships a warning (RAD40016) that flags patterns
which read like regexes but have no `regex=true`. Sweep every script you've run
recently:

```shell
rad check --from-logs all
```

The warning looks like this:

```
L4:17: WARN

     4 | fields = split(line, "\s+")
       |                 ^ '\s+' reads as a regex ('\s'), but split() matches
       |                   literally unless you pass regex=true. [...]
       |                 (code: RAD40016)
       = help: add regex=true to keep the old behavior [...]
```

**2. Add `regex=true` where you meant a regex.**

**3. Drop the escaping where you didn't.** Patterns that only existed to escape
metacharacters get simpler:

```rad
// Before
print(split("1.2.3", "\."))
// After
print(split("1.2.3", "."))
```

**4. Check your `replace()` replacements.** If a replacement string contains a `$`
that you wanted taken literally, it now works without a workaround. If it contains
a `$1` that you wanted expanded, the call needs `regex=true`.

### What the Warning Cannot Catch

RAD40016 only reads patterns that are written literally in your source. A pattern
held in a variable or built at runtime is invisible to it:

```rad
sep = get_env("FIELD_SEP")
parts = split("a b c", sep)   // no warning possible
```

It also stays quiet on patterns whose metacharacters are common in ordinary text,
`.` and a lone `|` in particular, because warning on those would bury the real
hits. If you have a script that assembles patterns dynamically, read it by hand.

### Group References in `replace()`

While making the replacement literal, the `$`-expansion under `regex=true` was
tightened up. Three long-standing bugs are fixed:

- `$10` used to be corrupted by the pass that substituted `$1`. Group 10 now works.
- A captured group whose own text contained something like `$2` used to get
  substituted a second time. Each output character is now written once.
- `$$` and `${1}` were not supported. They now are, meaning you can write a literal
  `$` and separate a group reference from a following digit.
- Groups came back empty when the pattern used an assertion that only held in
  context. `replace("abc abc", "\Bb(c)", "[$1]", regex=true)` produced `a[$1] a[$1]`
  and now produces `a[c] a[c]`.

The full rules are in the [`replace` reference](../reference/functions.md#replace).

## Breaking Change: Shell Commands Quote Interpolated Values

### What Changed

A value interpolated into a shell command now reaches the program as exactly one
argument, whatever characters it contains:

```rad
message = "it's fine"

$`git commit -m {message}`
// v0.11: git commit -m it's fine   ->  shell syntax error
// v0.12: git commit -m 'it'\''s fine'
```

The text you write is still shell. Pipes, redirects, `&&`, globs and `$VAR` in the
literal parts of the command all work exactly as before. Only the interpolations
changed.

Values made only of `A-Z a-z 0-9 @ % + = : , . / _ -` pass through unquoted, so
most commands produce byte-identical output to v0.11.

### Why

Hand-written quotes could never be correct for every value, and both spellings fail
on ordinary data:

| You wrote | Value | v0.11 result |
|---|---|---|
| `-m "{msg}"` | `it's` | works |
| `-m "{msg}"` | `100% of $USERS` | **silently** becomes `100% of ` |
| `-m '{msg}'` | `a b` | works |
| `-m '{msg}'` | `it's o'clock` | **silently** becomes `its oclock` |
| `-m {msg}` | `a b` | **silently** becomes two arguments |

There is no quoting a script can write in advance that survives every value,
because the correct quoting depends on the value. Rad knows the value at the moment
it interpolates, so it does the quoting there.

This also closes an injection route. A value from an HTTP response, a filename, or
an LLM could previously carry `; rm -rf ~` into a command and have it run.

### Migration Steps

**1. Find the affected commands.** RAD40023 flags interpolations wrapped in quotes
the script wrote itself:

```shell
rad check --from-logs all
```

**2. Delete your quotes.**

```rad
message = "hello"

// Before
$`git commit -m "{message}"`
// After
$`git commit -m {message}`
```

**3. Hoist arguments that mix literal text with a value.** The quotes were holding
the two halves together as one argument; a single interpolation does that alone:

```rad
version = "1.2.3"

// Before
$`git commit -m "Bump to {version}"`
// After
message = "Bump to {version}"
$`git commit -m {message}`
```

**4. Turn joined lists into real lists.** A list now expands to one argument per
element, each quoted separately, so the `join(" ")` workaround is obsolete - and it
was losing any element containing a space:

```rad
files = ["My Notes.txt", "b.txt"]

// Before - one argument, or several wrong ones
$`tar -czf out.tgz {files.join(" ")}`
// After - one argument per file
$`tar -czf out.tgz {files}`
```

An empty list contributes no arguments at all, which replaces the conditional
flag-fragment trick:

```rad
args:
    all bool

// Before
extra = all ? "--hidden --no-ignore" : ""
// After
extra = all ? ["--hidden", "--no-ignore"] : []
```

**5. Convert commands you assemble piecewise into lists.** Building a command as a
string and running it with `$cmd` still works and is still verbatim - Rad has no
interpolation to protect once the string exists. A list is safe and reads better:

```rad
args:
    start str?

path = "clip.mp4"

// Before
cmd = `ffmpeg -i '{path}'`
if start:
    cmd += " -ss {start}"
$cmd

// After
cmd = ["ffmpeg", "-i", path]
if start:
    cmd += ["-ss", start]
$cmd
```

### What the Diagnostic Cannot Catch

RAD40023 reads command *literals*. It cannot see a command assembled into a string
elsewhere and run with `$cmd`, because by then the interpolation has already
happened and there is nothing left to flag:

```rad
path = "a b.txt"

cmd = `ls '{path}'`   // no warning possible
$cmd
```

That form is unchanged in v0.12 - it was raw before and is raw now - but it is also
where the old quoting bugs live. If you have scripts that build command strings,
read them by hand and convert them to lists.

### New Errors

Two shapes that used to produce a mangled command now fail outright, both under
RAD20045:

- Interpolating a value with no single-argument form - a map, or a null that would
  have become the four-character word `null`. Use `??` to supply a fallback.
- Interpolating a list that isn't standing alone as its own argument, such as
  `--file={files}`, where there is no obvious answer to which element takes the
  prefix.
