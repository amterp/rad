# Migrating to Rad v0.12

Version 0.12 has seven breaking changes.

Two concern text you pass through Rad, and share a shape: each took a default that
quietly did the wrong thing, and now makes the safe reading the default instead.

- `split()` and `replace()` now match literally, with `regex=true` to opt back in.
- Values interpolated into a shell command are now quoted, so they arrive as one
  argument instead of as shell syntax.

One concerns what a shell command hands back:

- Capturing into names of your own now fills `(stdout, stderr, code)` instead of
  `(code, stdout, stderr)`.

Three concern how the command line is parsed:

- A list arg now collects every bare positional value, instead of filling a single
  slot.
- A `-`-prefixed token is no longer accepted as a flag's value.
- A constraint on a list or variadic arg is now enforced, having been accepted and
  ignored until now.

One concerns scripts that prompt:

- Run without a terminal, a script that can prompt now stops before executing
  anything, instead of running until it reaches the prompt.

Most of these can change what a script does without raising an error, so they are
worth reading rather than waiting to be told.

Four of the seven ship a diagnostic. To find every affected script you've run
recently:

```shell
rad check --from-logs all
```

The other three need no warning, for different reasons. A rejected flag-like
value fails loudly the moment it happens. A script that can prompt fails loudly
too, and lists what to do about it. A list arg swallowing a later positional is
the one that can pass silently, and there is no diagnostic for it - its section
below tells you how to spot it from your own `--help` output instead.

## Breaking Change: `split()` and `replace()` Match Literally

### What Changed

Both functions used to treat their pattern as a regex. Now they look for the exact
text you give them:

```rad
print(split("1.2.3", "."))          // v0.11: ["", "", "", "", ""]   v0.12: ["1", "2", "3"]
print(replace("a.b", ".", "-"))     // v0.11: "---"                  v0.12: "a-b"
```

Pass `regex=true` to get the old behavior:

```rad
print(split("a b  c", "\s+", regex=true))          // -> ["a", "b", "c"]
print(replace("order 66", "\d+", "N", regex=true)) // -> "order N"
```

`matches()` is unchanged. It exists to test patterns, so it's still always a regex.

### Why

Two reasons, and the second is the one that matters.

The first is that literal is what most calls want. Across a corpus of real Rad
scripts, 87% of `split` and `replace` calls passed a pattern with no regex
constructs in it. The default was serving the minority.

The second is how the two mistakes fail. Reaching for a literal when you needed a
regex gives you an obviously wrong answer that you notice immediately. Reaching for
a regex when you needed a literal corrupts quietly: a `.` matches every character,
a `$` in text you relayed from somewhere else eats your replacement. Silent
corruption is the worse failure, and it belonged to the old default.

### Two More Things Changed

**`replace()`'s replacement text is now literal too.** In the default mode, `$1`
and `$$` in the replacement are inserted as written. Previously they were always
interpreted, which meant relaying text through `replace()` could mangle it. Group
references still work under `regex=true`.

**`split()` no longer guesses.** It used to compile the separator as a regex and,
if that failed, silently fall back to a literal split. Whether a call was a regex
split or a literal one was decided at runtime by the shape of the input:

```rad
// v0.11
split("a.b", ".")    // -> ["", "", "", ""]  (a valid regex, so: regex)
split("a(b", "(")    // -> ["a", "b"]        (not a valid regex, so: literal)
```

Now the separator is literal unless you say otherwise, and under `regex=true` a
pattern that doesn't compile is an error.

### Migration Steps

**1. Find the affected calls.** Rad ships a warning (RAD40016) that flags patterns
which read like regexes but have no `regex=true`. Sweep every script you've run
recently:

```shell
rad check --from-logs all
```

The warning looks like this:

```
L4:17: WARN

     4 | fields = split(line, "\s+")
       |                 ^ '\s+' reads as a regex ('\s'), but split() matches
       |                   literally unless you pass regex=true. [...]
       |                 (code: RAD40016)
       = help: add regex=true to keep the old behavior [...]
```

**2. Add `regex=true` where you meant a regex.**

**3. Drop the escaping where you didn't.** Patterns that only existed to escape
metacharacters get simpler:

```rad
// Before
print(split("1.2.3", "\."))
// After
print(split("1.2.3", "."))
```

**4. Check your `replace()` replacements.** If a replacement string contains a `$`
that you wanted taken literally, it now works without a workaround. If it contains
a `$1` that you wanted expanded, the call needs `regex=true`.

### What the Warning Cannot Catch

RAD40016 only reads patterns that are written literally in your source. A pattern
held in a variable or built at runtime is invisible to it:

```rad
sep = get_env("FIELD_SEP")
parts = split("a b c", sep)   // no warning possible
```

It also stays quiet on patterns whose metacharacters are common in ordinary text,
`.` and a lone `|` in particular, because warning on those would bury the real
hits. If you have a script that assembles patterns dynamically, read it by hand.

### Group References in `replace()`

While making the replacement literal, the `$`-expansion under `regex=true` was
tightened up. Three long-standing bugs are fixed:

- `$10` used to be corrupted by the pass that substituted `$1`. Group 10 now works.
- A captured group whose own text contained something like `$2` used to get
  substituted a second time. Each output character is now written once.
- `$$` and `${1}` were not supported. They now are, meaning you can write a literal
  `$` and separate a group reference from a following digit.
- Groups came back empty when the pattern used an assertion that only held in
  context. `replace("abc abc", "\Bb(c)", "[$1]", regex=true)` produced `a[$1] a[$1]`
  and now produces `a[c] a[c]`.

The full rules are in the [`replace` reference](../reference/functions.md#replace).

## Breaking Change: Shell Commands Quote Interpolated Values

### What Changed

A value interpolated into a shell command now reaches the program as exactly one
argument, whatever characters it contains:

```rad
message = "it's fine"

$`git commit -m {message}`
// v0.11: git commit -m it's fine   ->  shell syntax error
// v0.12: git commit -m 'it'\''s fine'
```

The text you write is still shell. Pipes, redirects, `&&`, globs and `$VAR` in the
literal parts of the command all work exactly as before. Only the interpolations
changed.

Values made only of `A-Z a-z 0-9 @ % + = : , . / _ -` pass through unquoted, so
most commands produce byte-identical output to v0.11.

### Why

Hand-written quotes could never be correct for every value, and both spellings fail
on ordinary data:

| You wrote | Value | v0.11 result |
|---|---|---|
| `-m "{msg}"` | `it's` | works |
| `-m "{msg}"` | `100% of $USERS` | **silently** becomes `100% of ` |
| `-m '{msg}'` | `a b` | works |
| `-m '{msg}'` | `it's o'clock` | **silently** becomes `its oclock` |
| `-m {msg}` | `a b` | **silently** becomes two arguments |

There is no quoting a script can write in advance that survives every value,
because the correct quoting depends on the value. Rad knows the value at the moment
it interpolates, so it does the quoting there.

This also closes an injection route. A value from an HTTP response, a filename, or
an LLM could previously carry `; rm -rf ~` into a command and have it run.

### Migration Steps

**1. Find the affected commands.** RAD40023 flags interpolations wrapped in quotes
the script wrote itself:

```shell
rad check --from-logs all
```

**2. Delete your quotes.**

```rad
message = "hello"

// Before
$`git commit -m "{message}"`
// After
$`git commit -m {message}`
```

**3. Hoist arguments that mix literal text with a value.** The quotes were holding
the two halves together as one argument; a single interpolation does that alone:

```rad
version = "1.2.3"

// Before
$`git commit -m "Bump to {version}"`
// After
message = "Bump to {version}"
$`git commit -m {message}`
```

**4. Turn joined lists into real lists.** A list now expands to one argument per
element, each quoted separately, so the `join(" ")` workaround is obsolete - and it
was losing any element containing a space:

```rad
files = ["My Notes.txt", "b.txt"]

// Before - one argument, or several wrong ones
$`tar -czf out.tgz {files.join(" ")}`
// After - one argument per file
$`tar -czf out.tgz {files}`
```

An empty list contributes no arguments at all, which replaces the conditional
flag-fragment trick:

```rad
args:
    all bool

// Before
extra = all ? "--hidden --no-ignore" : ""
// After
extra = all ? ["--hidden", "--no-ignore"] : []
```

**5. Convert commands you assemble piecewise into lists.** Building a command as a
string and running it with `$cmd` still works and is still verbatim - Rad has no
interpolation to protect once the string exists. A list is safe and reads better:

```rad
args:
    start str?

path = "clip.mp4"

// Before
cmd = `ffmpeg -i '{path}'`
if start:
    cmd += " -ss {start}"
$cmd

// After
cmd = ["ffmpeg", "-i", path]
if start:
    cmd += ["-ss", start]
$cmd
```

### What the Diagnostic Cannot Catch

RAD40023 reads command *literals*. It cannot see a command assembled into a string
elsewhere and run with `$cmd`, because by then the interpolation has already
happened and there is nothing left to flag:

```rad
path = "a b.txt"

cmd = `ls '{path}'`   // no warning possible
$cmd
```

That form is unchanged in v0.12 - it was raw before and is raw now - but it is also
where the old quoting bugs live. If you have scripts that build command strings,
read them by hand and convert them to lists.

### New Errors

Two shapes that used to produce a mangled command now fail outright, both under
RAD20045:

- Interpolating a value with no single-argument form - a map, or a null that would
  have become the four-character word `null`. Use `??` to supply a fallback.
- Interpolating a list that isn't standing alone as its own argument, such as
  `--file={files}`, where there is no obvious answer to which element takes the
  prefix.

## Breaking Change: Positional Shell Captures Are Reordered

### What Changed

Shell commands produce stdout, stderr, and an exit code. When you capture them
into variables that *aren't* named `code`, `stdout`, or `stderr`, Rad fills them
by position - and that order has changed:

```rad
// v0.11: (code, stdout, stderr)     v0.12: (stdout, stderr, code)
out = $`rad -v`             // v0.11: 0            v0.12: "rad v0.12.0\n"
out, err = $`rad -v`        // v0.11: 0, output    v0.12: output, errors
out, err, c = $`rad -v`     // v0.11: 0, out, err  v0.12: out, err, 0
```

**Named assignment is unchanged.** If every variable in the statement is spelled
exactly `code`, `stdout`, or `stderr`, Rad assigns by name and always did:

```rad
code = $`cmd`                   // unchanged
stdout = $`cmd`                 // unchanged
code, stdout = $`cmd`           // unchanged
stderr, stdout, code = $`cmd`   // unchanged
```

### Why

Two reasons.

The first is that `out = $cmd` binding the exit code was the wrong answer to the
most natural-looking question. Every other language with a capture idiom - bash's
`$(...)`, Python's `check_output`, Ruby and Perl's backticks - gives you the
output. Rad gave you a number.

The second is that the number wasn't even useful. Rad assigns the capture
variables *before* it checks the exit code, and an unhandled non-zero exit stops
the script. So in `out = $cmd` with no `catch:`, `out` is `0` on every line that
can read it - it cannot be anything else. The most natural capture form was
reserved for the one value that carried no information.

Moving the code last also makes the two assignment rules agree. `stdout = $cmd`
used to mean stdout by name but the exit code by position; now both readings give
you stdout.

### Migration Steps

**1. Find the affected captures.** RAD40018 flags capture targets whose names
promise a different stream than they now receive:

```
L46:4: WARN

    46 | _, version = $`rad -v`
       |    ^ 'version' is bound to stderr here. [...] Before v0.12 the order
       |      was (code, stdout, stderr), so this used to bind stdout instead -
       |      same script, different variable, no error.
       |    (code: RAD40018)
```

**2. For mixed naming, rename rather than reorder.** The most common affected
shape uses a reserved name alongside an ordinary one, which drops the whole
statement to positional:

```rad
// Before - 'out' isn't reserved, so 'code' silently receives stdout
code, out = $`make test` catch:
    print_err("failed: {out}")

// After - now all names are reserved, so assignment goes by name
code, stdout = $`make test` catch:
    print_err("failed: {stdout}")
```

This is a rename, and it captures exactly the same streams as before. It's the
best fix for `code, out = ...` and `code, out, err = ...`.

**3. For discard-then-capture, drop a slot.** `_, x = $cmd` was the old idiom for
"skip the exit code, take stdout". Stdout is now first, so the `_` goes:

```rad
// Before
_, version = $`rad -v`
// After
version = $`rad -v`
```

Careful with the three-target form - the old middle slot is now the first:

```rad
// Before
_, output, _ = $`pwd`
// After
output = $`pwd`
```

**4. Check your silencing.** Discards follow the same order, so silencing needs
one fewer slot than it used to:

```rad
// Before: three slots to swallow both streams, two to swallow stdout
_, _, _ = $`cmd`
_, _ = $`cmd`

// After: one fewer each
_, _ = $`cmd`
_ = $`cmd`
```

### What the Warning Cannot Catch

RAD40018 reads variable names, so a positional capture whose names give no
signal either way is invisible to it:

```rad
a, b = $`cmd`   // no warning possible
```

It also stays deliberately quiet on names that are genuinely ambiguous. `status`
is the instructive one: it reads as "exit status", but `status = $`git status``
is a perfectly good v0.12 capture of stdout, so flagging it would fire on correct
new code. If a script captures into names like these, read it by hand.

## Breaking Change: List Args Collect Every Positional Value

### What Changed

A list arg used to fill exactly one positional slot. Now it collects every bare
value until the next flag:

```rad
args:
    targets str[]
```

```shell
./script a.txt b.txt c.txt
# v0.11: error, "Too many positional arguments. Unused: [b.txt, c.txt]"
# v0.12: targets = ["a.txt", "b.txt", "c.txt"]
```

Through its own flag nothing changed - `--targets a --targets b` is still how you
repeat it, and `--targets a b` still passes only `a`.

### Why

`./script a.txt b.txt c.txt` is what everyone types first, and it was the one
thing that didn't work. The fix was to declare the arg variadic (`*targets str`)
instead, which differs by a single character and was invisible from the error.
Now both spellings collect positionals, and they differ where it's meaningful:
after its own flag, a variadic is greedy and a list takes one value.

### What To Check

**An arg declared after a list arg can no longer be given positionally.** This is
the case that can move a value silently:

```rad
args:
    files str[]
    mode str = "fast"
```

```shell
./script a b
# v0.11: files = ["a"], mode = "b"
# v0.12: files = ["a", "b"], mode = "fast"
```

Where the later arg is required you'll get a missing-argument error, which is
loud. Where it has a default, as above, the value just moves. Run `--help`: if
the usage line ends at your list arg, everything declared after it is flag-only
now. Either reorder the declarations so the list comes last, or tell users to
pass the later arg by flag.

Scripts using `*variadic` args are unaffected.

## Breaking Change: Flag-Like Tokens Are Rejected As Values

### What Changed

A flag used to take whatever token followed it. Now a `-`-prefixed token is read
as a flag:

```shell
./script --name --verbose
# v0.11: name = "--verbose", and --verbose was never set
# v0.12: error
```

To pass a value that starts with `-`, use the `=` form (`--name=--verbose`) or
put it after `--`.

### Why

A mistyped flag became data, silently, and scripts were left hand-rolling their
own leading-dash checks to catch what the parser should have caught.

### What To Check

Negative numbers still work for number args, so `--count -5` is unaffected. The
carve-out is typed, though: for a `str` arg, `--name -5` is now an error and
`--name=-5` is how you write it. A bare `-` is still a value, so `--output -`
keeps working.

If your script hand-rolls a `starts_with(value, "-")` rejection, you can drop it.

## Breaking Change: Constraints On A List Are Enforced

### What Changed

`enum`, `regex` and `range` could be declared on a list or variadic arg. They
were accepted, shown nowhere, and never checked:

```rad
args:
    scores int[]
    scores range [0, 100]
```

```shell
./script --scores 5 --scores 500
# v0.11: scores = [5, 500]
# v0.12: error, "'scores' value 500 is > maximum 100"
```

On a list, a constraint describes each value. Every value has to pass, whether
it arrived through a repeated flag or as a bare positional. The constraint also
now appears in `--help`, where it showed a bare `--scores ints` before.

Declaring a constraint the arg's type cannot honor - `enum` on an `int[]`,
`range` on a `str[]` - is now an error, `RAD40024`. That check catches the same
mistake on scalar args, which were equally silently ignored: `age int` with
`age enum [...]` never did anything either.

### Why

A script that declares a constraint reads as though it validates its input.
Whoever wrote it stops checking by hand, because the args block says the work is
done. It wasn't: the constraint reached the argument parser and was dropped
there, and the values flowed into the script unexamined - into shell commands,
in the cases that prompted this.

Interactive mode had been checking these all along, so `rad -i` already rejected
what plain `rad` accepted. One of the two was wrong, and it wasn't the one doing
the checking.

### What To Check

Scripts that declare a constraint on a list and pass values violating it. Those
were already not doing what they said; they will now fail loudly.

Run `rad check` over your scripts to find the declarations that can never
apply:

```shell
rad check --from-logs all
```

### What the Diagnostic Cannot Catch

`RAD40024` finds constraints that don't fit their arg's type. It cannot tell you
that a constraint which *does* fit will now start rejecting values it previously
let through - that depends on what your users pass, not on what the script says.
If a script has a declared-but-ignored constraint that its callers have been
violating, the first sign will be the run that fails.

### New Syntax: `len`

Alongside this, `len` bounds how many values a list or variadic takes, using the
interval notation `range` already uses:

```rad
args:
    pair str[]
    *ports int

    pair len [2,2]      // exactly two
    ports len [1,]      // at least one
```

This is additive - no existing script is affected.

## Breaking Change: Scripts That Prompt Stop Before Running Without A Terminal

### What Changed

A script calling `input`, `confirm`, `pick`, `pick_kv`, `pick_from_resource`,
`multipick`, or a `confirm`-gated shell command used to run until it reached the
prompt and then fail. Now rad checks first, and refuses to start:

```rad
print("fetching")
env = pick(["dev", "prod"])
```

```shell
rad deploy.rad < /dev/null
# v0.11: prints "fetching", then error[RAD20000]: pick requires an interactive terminal
# v0.12: error[RAD20046], listing every prompt. Nothing runs.
```

Answer the prompts with [`--reply`](../guide/global-flags.md#reply), keyed by
line. Rad prints your own command back with a `--reply` per prompt, keys in
place and a blank where each answer goes.

Two things soften this. Rad now looks for a terminal on `/dev/tty` as well as
stdin, so `echo x | rad script.rad` and the `rad - --shell` Bash embedding both
prompt normally where they previously could not. And on a terminal nothing
changes at all: the check only runs when neither is available, which means CI,
cron, and AI agent tool calls.

### Why

A prompt reached halfway through a run has already done whatever the script did
to get there - fetched, written, deleted. The caller then has to work out what
completed before they can safely retry. Checking up front is the difference
between a run you can repeat and a run you have to unpick.

It also makes the answers possible. Rad has to know which prompts a script has
before it can accept answers for them, and knowing that is what `--reply` is
built on.

### What To Check

**A prompt on a branch this run won't take still counts.** Rad reads the script,
not the future, so it lists every prompt reachable from the command you invoked.
Where you know a prompt won't be hit, say so rather than inventing a value:

```shell
rad deploy.rad --dry-run --reply-na 20
```

Reaching it anyway fails cleanly (RAD20047) instead of acting on a guess.

**A `pick` given a filter is the case most likely to bite.** It narrows its
options first and never asks when exactly one survives, so this pattern works
today without a terminal:

```rad
args:
    name str

servers = ["web-1", "web-2"]
server = pick(servers, name)
```

Rad cannot evaluate `name` before running, so it lists the prompt and blocks.
Add `--reply-na <line>` for the runs where you expect the filter to resolve it.
The listing marks these `filtered - may not prompt` so they are easy to spot.

**`--confirm-shell` with no terminal is now refused outright.** It gates every
shell command, including ones rad cannot see in advance, so it cannot be
satisfied with `--reply`. Drop the flag, or run where a terminal exists.

Scripts with no interactive calls are unaffected, as are all runs on a terminal.

## Also Changed: `??` and `catch` See Errors You Already Hold

Not counted among the seven above - the old behavior was never the documented one - but
it can change a result, so it is worth knowing.

### What Changed

Both operators fired when a *call* failed, but ignored an error value sitting directly in
front of them:

```rad
r = error("boom") ?? "fallback"
// v0.11: r is the error. v0.12: r is "fallback"
```

The same applies to an error that a `catch:` block bound earlier:

```rad
fn fail() -> str|error:
    return error("boom")

stored = fail() catch:
    pass

r = stored catch "default"
// v0.11: r is the error. v0.12: r is "default"
```

### Why

The guide, the syntax reference, and the type checker all already specified that these
operators fire on an error. Only the interpreter disagreed. Rather than document the
exception, we removed it.

### What To Check

Nothing, unless a script deliberately used `??` or `catch` to pass an error *through*.
A held error is otherwise unchanged - returning it from a function still raises it there.
See [Holding an Error](../guide/error-handling.md#holding-an-error).
